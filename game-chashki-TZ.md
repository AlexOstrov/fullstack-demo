## 1. Цель проекта

Разработать веб-игру **«Русские шашки»** (8×8, обязательное взятие, правило большинства, дамки) с:

* надёжной и полностью соответствующей правилам игровой логикой на бэкенде;
* аккуратным, отзывчивым интерфейсом с анимациями на фронтенде;
* «живым» комментарием от LLM после каждого хода ИИ (характер, эмоции, лёгкие пояснения — без нарушения правил и без подсказки ходов);
* сохранением в PostgreSQL результата каждой завершённой партии (таблица `tournament`) и местом для избранных комментариев LLM (таблица `llm_comments`).

**Вне рамок проекта (явно не делаем, см. также Бэклог — раздел 16):** сетевая игра человек-человек, рейтинги, аутентификация пользователей, горизонтальное масштабирование, расширенные эндшпильные правила ничьей, хранение живого состояния партии в БД (живое состояние — только в памяти).

## 3. Правила игры «Русские шашки» — эталонная спецификация

Это нормативный раздел: игровая логика и тесты должны соответствовать ему буквально.

### 3.1. Доска и расстановка

* Доска 8×8. Игровыми являются тёмные клетки, где `(row + col)` — нечётное.
* Координаты: `row` 0..7 сверху вниз, `col` 0..7 слева направо (0-based). Координаты фиксированы независимо от цвета игрока; меняется только визуальная ориентация доски.
* Начальная расстановка: белые занимают тёмные клетки рядов 5–7 (12 шашек), чёрные — рядов 0–2 (12 шашек).
* Белые ходят «вверх» (уменьшение `row`), чёрные — «вниз» (увеличение `row`).

### 3.2. Ход простой шашки

* Простая шашка ходит по диагонали **вперёд** на одну свободную клетку.
* Простая шашка **бьёт и вперёд, и назад**.

### 3.3. Ход дамки

* Дамка ходит по диагонали на любое количество свободных клеток.
* Дамка бьёт по диагонали, **перепрыгивая ровно одну** шашку соперника и приземляясь на любую свободную клетку за ней (до следующей занятой клетки).

### 3.4. Взятие

* Взятие **обязательно**: если есть хотя бы одно взятие, все простые ходы запрещены.
* **Правило большинства:** из всех доступных взятий допустимо только то (те), что берут **максимальное** число шашек. Меньшие взятия запрещены.
* Взятие серийное: последовательность прыжков выполняется в рамках **одного хода**.
* Взятая шашка **снимается с доски сразу** после прыжка (вариант русских шашек). Это автоматически запрещает бить одну и ту же шашку дважды.
* Взятие обязательно и в том случае, если оно невыгодно (например, ведёт к проигрышу материала).

### 3.5. Превращение в дамку

* Простая шашка, завершившая ход на последней горизонтали соперника (белая — `row 0`, чёрная — `row 7`), становится дамкой.
* Если превращение происходит **в ходе серийного взятия** и после него ещё возможно продолжение боя (теперь уже как дамка), превращение происходит немедленно и бой продолжается как дамка. Если продолжения нет — бой заканчивается, шашка остаётся дамкой на этой клетке.

### 3.6. Окончание партии

* Если у игрока, чей ход, **нет допустимых ходов**, он проигрывает.
* Ничья фиксируется в случаях:
  * **троекратное повторение** одной и той же позиции (одинаковая расстановка и один и тот же игрок, чей ход);
  * **15 ходов** (по 15 на каждого игрока, то есть 30 полуходов) подряд сделаны **только дамками**, без взятий и без ходов простыми шашками;
  * **ничья по согласию** (оба игрока согласились).
* Правило «50 ходов без взятий» (шахматное) **не применяется**.
* Сдача (resign) фиксирует поражение сдавшегося.

> **Явно вне рамок:** расширенные эндшпильные правила ничьей (например, «3 дамки против 1», «2 дамки против 1») **не реализуются**. Партия с малым материалом завершается только по общим правилам (нет ходов / повторение / 15 ходов дамками / согласие).

## 4. Игровая логика (Backend)

### 4.1. Модель состояния

Состояние партии (in-memory объект):

* `id`: UUID партии.
* `board`: `8×8`, значения — перечисление `EMPTY`, `WHITE_MAN`, `BLACK_MAN`, `WHITE_KING`, `BLACK_KING`.
* `humanColor`: `WHITE` | `BLACK` — выбранный игроком цвет.
* `aiColor`: противоположный `humanColor`.
* `currentPlayer`: `WHITE` | `BLACK`.
* `status`: `IN_PROGRESS`, `WHITE_WON`, `BLACK_WON`, `DRAW`.
* `moveNumber`: номер хода (для порядка и идемпотентности).
* `lastMove`: путь и тип последнего хода (`NORMAL`, `CAPTURE`, `PROMOTION`).
* `history`: список применённых ходов (для UI и контекста LLM).
* `comments`: список комментариев LLM (по ходу ИИ).
* Счётчики для ничьей: таблица повторений позиций (Zobrist/строка-ключ), счётчик «дамки без взятий».
* `version`: версия состояния (монотонно растёт) — для защиты от устаревших запросов.

### 4.2. Живое состояние партии (in-memory)

* Реестр партий: `ConcurrentHashMap<UUID, GameState>`.
* Изоляция по партии: per-game блокировка (`ReentrantLock` в объекте партии) — исключает гонки при одновременных `move`/`ai-move`.
* Вытеснение: TTL неактивных партий (по умолчанию 60 минут) фоновой задачей; при перезапуске бэкенда незавершённые партии теряются — это осознанное ограничение движка.
* Однопроцессный режим (горизонтальное масштабирование не поддерживается).
* **В БД живые партии не хранятся.** Персистентности подлежат только завершённые партии (результат) и избранные комментарии LLM — см. 4.7.

### 4.3. Формат хода и координаты

Ход описывается **полным путём** (необходимо для серийных взятий):

```json
{
  "path": [
    { "row": 6, "col": 1 },
    { "row": 5, "col": 0 }
  ]
}
```

* `path` содержит последовательность клеток, которые посещает шашка, начиная с текущей и заканчивая конечной.
* Для обычного хода — 2 точки; для серийного взятия — 3 и более.
* Клиент отправляет путь целиком; сервер валидирует весь путь как один ход.

### 4.4. Валидация ходов

Валидатор возвращает:

* список допустимых ходов для текущего игрока (уже отфильтрованный правилом большинства);
* флаг `forcedCapture` и список ходов-взятий.

Правила валидации: раздел 3 + проверки «ход адресован существующей своей шашке», «путь непрерывен по диагонали», «промежуточные точки при взятии/движении корректны», «партия в статусе `IN_PROGRESS`», «ход за игрока, чья очередь».

### 4.5. Применение хода

* Применить путь, сняв взятые шашки по мере прыжка.
* Отработать превращение (в т.ч. в бою — раздел 3.5).
* Обновить счётчики повторений и «дамки без взятий», инкрементировать `moveNumber` и `version`, сменить `currentPlayer`.
* Определить конец партии (раздел 3.6).

### 4.6. Генератор ходов (общий для валидатора и минимакса)

Единая функция генерации, используемая и в API, и в ИИ, — исключает расхождение правил. Обязательно покрыта тестами (раздел 12).

### 4.7. Персистентность результатов и комментариев (PostgreSQL + Flyway)

Назначение БД: хранение **результата завершённых партий** и **избранных комментариев LLM**. Живое состояние — в памяти (4.2).

Схема создаётся новыми Flyway-миграциями; применённые миграции не редактируются.

**Текущая область — таблица `tournament`** (результат завершённой партии):

| Колонка | Тип | Описание |
|---------|-----|----------|
| `id` | BIGINT identity PK | |
| `game_id` | UUID NOT NULL UNIQUE | идентификатор партии |
| `winner` | VARCHAR(8) NOT NULL | `HUMAN` / `AI` / `DRAW` |
| `winner_color` | VARCHAR(8) NULL | `WHITE` / `BLACK`; `NULL` при ничьей |
| `human_color` | VARCHAR(8) NOT NULL | цвет игрока (для будущей статистики) |
| `duration_seconds` | INT NOT NULL | время игры |
| `moves_count` | INT NOT NULL | число сделанных ходов |
| `end_reason` | VARCHAR(24) NOT NULL | `NO_MOVES` / `RESIGN` / `DRAW_REPETITION` / `DRAW_KINGS` / `DRAW_AGREEMENT` |
| `finished_at` | TIMESTAMPTZ NOT NULL DEFAULT now() | момент завершения |

Запись создаётся **автоматически** при завершении партии (победа, ничья, сдача) — отдельный вызов из UI не требуется.

**Бэклог — таблица `llm_comments`** (избранные комментарии LLM, см. раздел 16, B2). Схема проектируется сейчас, запись подключается вместе с UI лайков:

| Колонка | Тип | Описание |
|---------|-----|----------|
| `id` | BIGINT identity PK | |
| `comment` | TEXT NOT NULL | текст комментария |
| `style` | VARCHAR(32) NOT NULL | стиль комментария |
| `emotion` | VARCHAR(32) | эмоция |
| `llm_model` | VARCHAR(128) | модель, сгенерировавшая комментарий |
| `move_number` | INT | номер хода |
| `created_at` | TIMESTAMPTZ NOT NULL DEFAULT now() | |

Доступ к данным — через Spring Data JPA (`TournamentRepository`, `LlmCommentRepository`) и сервисный слой; `ddl-auto: validate` (схему задаёт только Flyway).

## 5. API (REST)

**Базовый путь:** `/api` (согласно `AGENTS.md`). Эндпоинты партий — `/api/game/...`, конфигурация — `/api/config/...`.

| Метод | Путь | Назначение |
|-------|------|------------|
| POST | `/api/game/start` | Создать партию с настройками (цвет, сложность, стиль, модель LLM), вернуть `id` и состояние. |
| GET | `/api/game/{id}` | Текущее состояние партии. |
| GET | `/api/game/{id}/moves` | История ходов и комментариев. |
| POST | `/api/game/{id}/move` | Ход игрока (валидация + применение + конец игры). |
| POST | `/api/game/{id}/ai-move` | Ход ИИ: минимакс → ход → комментарий LLM → новое состояние. |
| POST | `/api/game/{id}/resign` | Сдаться (поражение). |
| POST | `/api/game/{id}/draw` | Предложить/принять ничью. |
| POST | `/api/game/{id}/restart` | Начать партию заново (можно сменить настройки). |
| GET | `/api/config/llm-models` | Предустановленный список моделей LLM для селектора в UI. |

### 5.1. DTO (Java records + Jakarta Validation)

```java
public enum PieceColor { WHITE, BLACK }
public enum Difficulty { EASY, MEDIUM, HARD, CUSTOM }
public enum CommentaryStyle { FRIENDLY_MASTER, COMPETITIVE, NEUTRAL }

public record StartGameRequest(
    @NotNull PieceColor playerColor,
    @NotNull Difficulty difficulty,               // пресет глубины/бюджета (6.1)
    @Min(1) @Max(12) Integer aiDepth,             // только для CUSTOM
    @Min(200) @Max(5000) Integer aiTimeBudgetMs,  // только для CUSTOM
    @NotNull CommentaryStyle commentaryStyle,
    @NotBlank String llmModel                     // из GET /api/config/llm-models
) {}

public record MoveRequest(
    @NotEmpty List<Cell> path,
    @PositiveOrZero int clientMoveNumber
) {}

public record Cell(@Min(0) @Max(7) int row, @Min(0) @Max(7) int col) {}

public record LlmModelsResponse(
    @NotNull List<String> models,
    @NotBlank String defaultModel
) {}
```

Все DTO — `record`, поля валидируются Jakarta Validation. Ответы — тоже `record`.

### 5.2. Ответ на ход

```json
{
  "gameId": "uuid",
  "humanColor": "WHITE",
  "status": "IN_PROGRESS",
  "currentPlayer": "BLACK",
  "moveNumber": 2,
  "version": 2,
  "board": [["","b","", "..."], "..."],
  "lastMove": { "path": [{"row":6,"col":1},{"row":5,"col":0}], "type": "NORMAL" },
  "legalMoves": [ { "path": [{"row":2,"col":1},{"row":3,"col":0}] } ],
  "forcedCapture": false,
  "ai": {
    "move": { "path": [{"row":2,"col":1},{"row":3,"col":0}] },
    "comment": "Начинаю с осторожного хода, посмотрим на твои планы.",
    "emotion": "focused",
    "commentSource": "LLM"
  }
}
```

* Поле `ai` присутствует только в ответе `ai-move`.
* `commentSource`: `LLM` | `FALLBACK` — прозрачность для UI и тестов.

### 5.3. Формат ошибок

```json
{
  "timestamp": "2026-10-17T10:00:00Z",
  "status": 400,
  "code": "INVALID_MOVE",
  "message": "Обязательное взятие: доступно взятие 2 шашек.",
  "path": "/api/game/{id}/move"
}
```

Коды: `GAME_NOT_FOUND`, `NOT_YOUR_TURN`, `INVALID_MOVE`, `STALE_STATE`, `GAME_FINISHED`, `AI_BUSY`, `VALIDATION_ERROR`.

### 5.4. Идемпотентность и защита от гонок

* `clientMoveNumber` сверяется с текущим `moveNumber`; при несовпадении — `STALE_STATE`.
* Каждая партия обрабатывается под per-game блокировкой: повторный `ai-move` во время активного хода ИИ возвращает `AI_BUSY`.
* `ai-move` корректен только когда очередь ИИ; иначе — `NOT_YOUR_TURN` (AI_BUSY, если ход уже считается).

### 5.5. Персистентность и эндпоинты бэклога

* Результат завершённой партии сохраняется в таблицу `tournament` **автоматически** при переходе `status` в терминальное состояние (см. 4.7); отдельный вызов из UI не требуется.
* В Бэклоге (раздел 16) — эндпоинты: `GET /api/tournament` (статистика побед «человек/ИИ») и `POST /api/game/{id}/comments/{commentId}/like` (сохранить понравившийся комментарий в `llm_comments`).

## 6. ИИ-оппонент (минимакс + альфа-бета)

**Алгоритм:**

* Глубина поиска: задаётся пресетом сложности (4–6 полуходов для `MEDIUM`/`HARD`; 1–12 для `CUSTOM`, см. 6.1); всегда с итеративным углублением до исчерпания бюджета времени.
* Бюджет времени на ход: по умолчанию 1500 мс, максимум — 5000 мс (пресеты `AI_PRESET_*`).
* Альфа-бета отсечение.
* **Итеративное углубление** — гарантирует ответ при любом бюджете.
* **Сортировка ходов:** сначала взятия (и особенно с максимальным числом снятых шашек), затем TT-ход, затем «убийственные» ходы, затем прочие.
* **Транспозиционная таблица** на Zobrist-хэшах: кэш оценки + лучший ход; ограниченный размер (настраиваемый).
* Учёт правила большинства в генерации ходов (общая функция, раздел 4.6) — все продолжения серийного боя трактуются как один ход.
* Определение ничьей по повторению внутри поиска (обрезка).

**Эвристика оценки позиции:**

* Материал: простая = 100, **дамка = 300** (фиксированное значение).
* Продвижение простых к превращению.
* Безопасность: бонус за шашки на бортах (`col` 0 и 7) и в тылу; штраф за шашки под боем.
* Мобильность: разница числа доступных ходов (с учётом обязательного взятия).
* «Центр»: небольшой бонус **только для дамок**; для простых центр не поощряется.
* Темп/очередь хода.

### 6.1. Пресеты сложности (настраиваются в UI)

| Пресет | `aiDepth` (полуходы) | `aiTimeBudgetMs` | Назначение |
|--------|----------------------|------------------|------------|
| `EASY` | 2 | 500 | Новичок, быстрый ответ. |
| `MEDIUM` | 4 | 1500 | По умолчанию. |
| `HARD` | 6 | 3000 | Сильный соперник. |
| `CUSTOM` | 1–12 (из запроса) | 200–5000 (из запроса) | Ручная настройка. |

Пресет выбирается при старте партии (`StartGameRequest.difficulty`) и может быть изменён при `restart`. Значения пресетов конфигурируемы через env (`AI_PRESET_*`).

## 7. LLM-сервис (комментатор)

**Вариант реализации:** отдельный микросервис `llm-service`, проксирующий запросы к Ollama. Обоснование: изоляция модели, замена провайдера без правок бэкенда, единая точка таймаутов/retry.

### 7.1. Аппаратный профиль и выбор модели Ollama

Профиль целевого ПЭВМ (из `ps-hard.txt`):

* CPU: **AMD Ryzen 7 8845HS**, 8 ядер / 16 потоков (Zen 4, AVX-512), ~3.5 ГГц.
* GPU: **AMD Radeon 780M** — встроенный (UMA), выделенной VRAM нет (~512 МБ зарезервировано); на Windows ускорение Ollama через ROCm/Vulkan ограничено.
* ОЗУ: **32 ГБ** (доступно ~22 ГБ).
* ОС: Windows 11.

**Вывод:** выделенного GPU нет → инференс преимущественно **на CPU** (упирается в пропускную способность памяти). Ориентир — компактные модели 3B–8B в квантовании `Q4_K_M`.

**Рекомендуемая модель (тег Ollama, свободно доступен в публичной библиотеке):**

| Приоритет | Тег | Размер (Q4) | ОЗУ | Ожидаемая скорость (CPU, 16 потоков) | Комментарий |
|-----------|-----|-------------|-----|--------------------------------------|-------------|
| **По умолчанию** | `qwen2.5:7b-instruct` | ~4.7 ГБ | ~6–7 ГБ | ~7–10 tok/s | Баланс качества и скорости для короткого комментария. |
| Быстрый | `qwen2.5:3b-instruct` | ~1.9 ГБ | ~3 ГБ | ~20–30 tok/s | Если задержка важнее качества. |
| Альтернатива | `qwen3:4b` | ~2.6 ГБ | ~4 ГБ | ~15–20 tok/s | Компромисс. |
| Альтернатива | `qwen3:8b` | ~5.2 ГБ | ~7 ГБ | ~6–9 tok/s | Чуть выше качество. |
| ❌ Не использовать | модели ≥14B (напр., 27B) | ≥15 ГБ | ≥18 ГБ | ~1–2 tok/s | Неприемлемо медленно на CPU. |

Модель задаётся **параметром** (`LLM_MODEL`, значение по умолчанию — `qwen2.5:7b-instruct`) и **выбирается пользователем в UI** из списка `GET /api/config/llm-models`; смена модели не требует правок кода бэкенда.

**Эксплуатация:**

* `OLLAMA_KEEP_ALIVE` — держать модель в памяти между ходами (например, `10m`), чтобы избежать холодного старта.
* Выгрузка модели из памяти при необходимости: `ollama stop <model>`; проверка: `ollama ps`.
* Частичный оффлоад на iGPU (Vulkan/ROCm) — опционально, best-effort; не является требованием.

### 7.2. Конфигурация и список моделей

**env-параметры:** `OLLAMA_BASE_URL`, `LLM_MODEL` (по умолчанию `qwen2.5:7b-instruct`), `LLM_ALLOWED_MODELS` (список допустимых моделей через запятую), `LLM_TIMEOUT_MS` (8000), `LLM_MAX_RETRIES` (1), `LLM_TEMPERATURE` (0.7), `LLM_NUM_CTX` (2048), `LLM_ENABLED`, `OLLAMA_KEEP_ALIVE` (10m).

**Список моделей для UI:** `llm-service` предоставляет перечень доступных моделей (запрос `GET /api/tags` к Ollama, пересечённый с allowlist `LLM_ALLOWED_MODELS`); бэкенд отдаёт его через `GET /api/config/llm-models` вместе со значением по умолчанию. Выбранная модель сохраняется в состоянии партии и передаётся в каждый запрос к `llm-service`. Пример пресета: `qwen2.5:7b-instruct`, `qwen2.5:3b-instruct`, `qwen3:4b`, `qwen3:8b`.

### 7.3. Входные данные (JSON)

```json
{
  "gameId": "uuid",
  "moveNumber": 4,
  "currentPlayer": "BLACK",
  "aiPlayer": "BLACK",
  "move": {
    "path": [{"row": 3, "col": 2}, {"row": 5, "col": 4}],
    "isCapture": true,
    "captures": 1,
    "becomesKing": false
  },
  "boardState": {
    "board": [["", "b", "", "b", "", "b", "", "b"]],
    "turn": "WHITE",
    "moveNumber": 5,
    "kings": { "WHITE": 0, "BLACK": 0 }
  },
  "material": { "WHITE": 380, "BLACK": 340 },
  "commentaryStyle": "friendly_master",
  "llmModel": "qwen2.5:7b-instruct",
  "recentComments": ["..."]
}
```

* `boardState` — **компактный JSON** (не «FEN-like»): токены `""`, `"w"`, `"W"`, `"b"`, `"B"`.
* `commentaryStyle` выбирается пользователем в UI (см. 8.1).

### 7.4. Стили комментариев

* `friendly_master` — опытный, доброжелательный, короткие советы.
* `competitive` — азартный соперник, слегка «поддевает».
* `neutral` — сухие факты.

### 7.5. Формат ответа (JSON)

```json
{
  "comment": "Хороший ход! Придётся отступить, но я ещё поборюсь.",
  "style": "friendly_master",
  "emotion": "concerned"
}
```

* `emotion` — из фиксированного набора: `neutral`, `confident`, `happy`, `concerned`, `surprised`, `focused`, `playful`.

### 7.6. Ограничения и пост-валидация

* Не предлагать ходы, не менять правила, не упоминать варианты, кроме уже сделанного хода.
* Длина: **до 2 предложений, не более 160 символов**.
* Запрещён токсичный контент и любые «подсказки», нарушающие правила.
* **Пост-валидация (на бэкенде/сервисе):** отклоняем/перезапрашиваем ответ, если он содержит шахматно-шашечную нотацию ходов, превышает лимит длины, содержит стоп-слова либо не проходит JSON-схему.
* **Схема ответа** (structured output) фиксируется; несоответствие — повод для 1 retry, затем fallback.

### 7.7. Таймауты и fallback

* Таймаут LLM — 8000 мс, 1 retry. Бэкенд никогда не блокирует партию ожиданием LLM.
* **Fallback (обязателен):** при недоступности/таймауте/невалидном ответе используется детерминированный шаблонный комментарий по типу хода и стилю; в ответе `commentSource: "FALLBACK"`.
* UI показывает индикатор загрузки, но не более таймаута.

### 7.8. Промпт-шаблон

> Ты — комментатор в игре «Русские шашки». Опиши только что сделанный ход ИИ-игрока, передай его эмоции и кратко поясни мотив. Не предлагай других ходов и не меняй правила. Стиль: {style}. Длина: до 2 предложений. Ответ — строго в формате JSON по схеме.

## 9. Инфраструктура и запуск (Docker)

3. Запустить `llm-service`.
4. Запустить `backend`.

## 10. Нефункциональные требования

* **Производительность:** ход игрока — до 200 мс; ход ИИ — до 5 с; комментарий LLM — до 8 с (при превышении — fallback).
* **Отказоустойчивость:** недоступность LLM никогда не блокирует партию.
* **Конкурентность:** per-game блокировка, проверка `clientMoveNumber`, `AI_BUSY`.
* **Память:** TTL-вытеснение партий; транспозиционная таблица ограничена по размеру.
* **База данных:** пул соединений (HikariCP), миграции Flyway применяются при старте, `ddl-auto: validate`; запись результата партии — вне критического пути ответа (best-effort, не ломает партию при сбое БД).
* **Безопасность:** Jakarta Validation на входных DTO; секреты — только через env; в репозитории секретов нет.
* **Логирование:** структурированные логи (создание/ход/ИИ/LLM/ошибки/персистентность) без утечки секретов и персональных данных.
* **Ограничение платформы:** живое состояние в памяти → один экземпляр бэкенда, незавершённые партии теряются при перезапуске; завершённые партии сохраняются в PostgreSQL.

## 11. Артефактная память (процесс разработки)

**Проблема:** при старте новой сессии агент тратит время на повторный анализ всего проекта.

**Решение:** после каждой реализованной фичи максимально компактно фиксировать текущее состояние в каталоге `docs/memory/`. Новая сессия читает `STATE.md` и продолжает с последней точки без полного анализа.

### 11.1. Артефакты

| Файл | Назначение | Обновляется |
|------|------------|-------------|
| `docs/memory/STATE.md` | «Точка возобновления» (≤ 1 экран): текущий спринт/задача, последняя завершённая фича, следующая задача, блокеры, команды запуска, ссылки на ключевые файлы. | После каждой фичи |
| `docs/memory/FEATURES.md` | Журнал фич: ID, спринт, название, статус, файлы, тесты/DoD, коммит, дата. | После каждой фичи |
| `docs/memory/DECISIONS.md` | ADR: контекст, решение, альтернативы, следствия. | При принятии решения |
| `docs/memory/RUNBOOK.md` | Как запускать и проверять (Ollama, backend, frontend, docker, тесты). | При изменении запуска |

### 11.2. Правила

* **Definition of Done фичи включает обновление памяти** (STATE.md + строка в FEATURES.md).
* Новая сессия начинается с чтения `STATE.md`; `FEATURES.md`/`DECISIONS.md` — по необходимости.
* Формат записей фиксирован (шаблоны в 11.3), STATE.md поддерживается коротким.
* Совершать коммиты в формате Conventional Commits (русский), хэш фиксировать в FEATURES.md.
* `AGENTS.md` содержит указание «при старте сессии сначала прочитать `docs/memory/STATE.md`» — так память подхватывается автоматически.

### 11.3. Шаблоны

**STATE.md:**

```md
# Состояние разработки
## Сейчас
- Спринт / задача:
- В работе:
- Следующая задача:
## Последняя завершённая фича
- ID, название, коммит
## Блокеры
## Ссылки (ключевые файлы)
```

**Строка FEATURES.md:**

```md
| F-012 | Sprint 3 | POST /api/game/{id}/move | Done | GameController.java, MoveService.java | IT: move.spec.ts (5 зелёных) | a1b2c3d | 2026-10-20 |
```

## 12. Тестирование

**Unit-тесты (Java):**

* Валидация ходов: обычный ход, взятие, серия взятий, дамка (движение и бой), превращение, **превращение в бою**, **правило большинства**, запрет бить одну шашку дважды.
* Определение конца партии: отсутствие ходов, троекратное повторение, 15 ходов дамками, согласие/сдача.
* Минимакс: выбор лучшего хода на заранее известных позициях.

**Интеграционные тесты:**

* Полный цикл: старт → ход игрока → ход ИИ → комментарий → конец партии (для обоих цветов игрока, для каждого пресета сложности).
* Настройки партии: выбранные сложность, стиль и модель LLM применяются; `GET /api/config/llm-models` возвращает непустой список.
* Fallback: LLM недоступен — партия продолжается с `commentSource: "FALLBACK"`.
* Гонки: повторный `ai-move` → `AI_BUSY`; устаревший `clientMoveNumber` → `STALE_STATE`.
* Пост-валидация ответа LLM (стоп-слова, длина, схема).
* Персистентность: после завершения партии (победа/ничья/сдача) в `tournament` появляется ровно одна запись с корректными `winner`, `winner_color`, `human_color`, `duration_seconds`, `end_reason`; при недоступности БД партия всё равно завершается корректно.
* Flyway: миграции применяются на чистой БД; JPA-маппинг соответствует схеме (`ddl-auto: validate` не падает).

**UI-тесты (React Testing Library):**

* Отрисовка доски и шашек; подсветка ходов; отображение комментариев; индикатор загрузки; смена цвета и ориентация доски; работа селекторов сложности/стиля/модели.

## 13. Критерии приёмки

* Игра корректно применяет правила русских шашек: обязательное взятие, **правило большинства**, серийные взятия, превращение (в т.ч. в бою), ничья (повторение/дамки/согласие).
* Игрок может выбрать цвет; ИИ играет противоположным; доска ориентирована под игрока.
* Игрок может настроить сложность ИИ и выбрать модель LLM из списка; настройки применяются в партии.
* Ход ИИ всегда валиден и выбирается алгоритмом в рамках бюджета времени.
* Комментарий LLM соответствует стилю, не нарушает правила, не предлагает ходы; при сбое LLM партия не ломается (fallback).
* API соответствует контракту (раздел 5), коды ошибок корректны, гонки защищены.
* Результат каждой завершённой партии сохранён в таблице `tournament` (победитель, цвет победителя, длительность игры).
* Интерфейс отзывчивый, анимации плавные, визуальных ошибок нет.
* Приложение запускается в Docker и работает в браузере.
* Артефактная память актуальна: `STATE.md`/`FEATURES.md` отражают последнюю итерацию.

## 14. Спринты (детализированный план)

### Sprint 0. Инициализация: переиспользование каркаса и инфраструктура
**Цель:** подготовить существующий каркас к работе, очистить его и зафиксировать процесс.
**Задачи:**
1. Backend: подтвердить и зафиксировать существующий каркас `com.example.backend` (Spring Boot 4.1.1, Java 21, Maven), убрать дубли-файлы вне `src` (`backend/config/CordConfig.java`, `backend/controller/*`, `backend/dto/*`, `backend/repository/*`); слить `application.properties` в `application.yml`.

## 15. Принятые решения и открытые вопросы

**Принятые решения:**

* **Живое состояние партии — в памяти**; **результаты завершённых партий — в PostgreSQL** (`tournament`), избранные комментарии LLM — в `llm_comments` (раздел 4.7).
* Стек выровнен на существующий каркас: **Spring Boot 4.1.1**, Java 21, `jakarta.*`, Spring Data JPA, Flyway, PostgreSQL 16 (`app/app`).
* Базовый путь API — `/api` (согласовано с `AGENTS.md`).
* **Цвет игрока выбирается** при старте; ИИ играет противоположным; доска ориентируется под игрока.
* **Сложность ИИ настраивается в UI** (пресеты `EASY`/`MEDIUM`/`HARD`/`CUSTOM`, раздел 6.1).
* **Модель LLM выбирается в UI** из списка `GET /api/config/llm-models`; выбор применяется в партии.
* Ход передаётся полным путём (`path`) — покрывает серийные взятия.
* LLM — отдельный `llm-service` поверх Ollama; обязательный fallback.
* Модель Ollama задаётся параметром `LLM_MODEL`; по умолчанию `qwen2.5:7b-instruct` (профиль раздела 7.1, инференс на CPU).
* Дамка = 300 (фикс); центр поощряется только для дамок.
* Ничья: троекратное повторение, 15 ходов дамками, согласие. Правило «50 ходов» не применяется.
* Расширенные эндшпильные правила ничьей **не реализуются**.
* Ведётся **Артефактная память** (`docs/memory/`) — см. раздел 11.
* Сбор статистики «человек/ИИ», лайки комментариев и их случайный fallback — в **Бэклоге** (раздел 16).

**Открытые вопросы:** нет — ТЗ финализировано (v2.4); перспективные доработки вынесены в Бэклог (раздел 16).
